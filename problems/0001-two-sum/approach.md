# 解答方針 — 1. Two Sum

## 問題の整理

- 入力: n要素配列, ターゲット数値
- 出力: 配列の中の二つのインデックスを返す（対応する値の合計がターゲット数値になる一意の組み合わせ）
- 制約から読み取れること: 配列はソートされていない。一意の回になるので、一つ解を見つけたら終了していい。2つのインデックスが同一である可能性も否定できないようにみえるが、ひとまず除外

## 方針 1

単純な実装では、全てのパターンを走査
nから2を選ぶので、 n(n-1)/2, O(n**2)回、配列要素の足し算を行い、ターゲット数値と合うかを見ていく

nums[0]+nums[1] =? target
nums[0]+nums[2] =? target
...
nums[n-2]+nums[n-1] =? target

## 方針 2

ひとまず配列をソートする n*log(n)
すると、尺取り法でO(n)で探索が終了する

numsを昇順にソート

nums[0]+nums[n-1] > target と仮定する（この等号が逆の場合も同様）

nums[0]+nums[n-1] > target
nums[0]+nums[n-2] > target
...(どこかで、targetと逆転・あるいは一致)
if:
    nums[0]+nums[x] == target -> 答えが見つかった、探索を打ち切る
else:
    nums[0]+nums[x] < target -> いままで見てきた nums[x+1]~nums[n-1]は除外してよい（なぜなら、最小のnums[0]とたしてもtargetをoverするので、どうやってもtargetと一致しない）

nums[1]+nums[x] に進む
if:
    nums[1]+nums[x] > target -> nums[0] の時と同様に、右辺のインデックスを x -> x-1 -> ..と減らしてい
elif:
    nums[1]+nums[x] == target -> 答えが見つかった、探索を打ち切る
else:
    nums[1]+nums[x] < target -> nums[1] ではまだ小さい。左辺のインデックスを2に上げる

## 方針2改善

- `pairs = sorted((v, i) for i, v in enumerate(nums))` を使って、インデックスを付与した値に対して、ソート
    これにより、目的の要素が見つかったときに元のインデックスがO(1)で見つかる

- インデックスがないは、割り切っても問題ない。要素が見つかってから対象となるインデックスをみつけるのはたかだかO(N)こんかいはソートのO(n*log(n))が支配的なので問題ない

- ループの終了条件を l == r のように誤っておかず、 l > r のようにすれば問題ない（l > r になるまえに、l == r になり、必ずその周回までで答えがでる）

### 2026-10-24

**問題の整理**

- 「2 つのインデックスが同一である可能性」は、問題文の *you may not use the same element twice* で明示的に否定されている。除外して正解。
  ただし **値が同じ 2 要素** は普通にありうる（Example 3: `[3, 3]`）。「インデックスが違う」と「値が違う」を混同しないように。
- 「解は 1 つだけ」なので、見つけ次第 return してよいという読みも正しい。

**方針 1（全探索）**

- 組み合わせ数 n(n−1)/2、O(n²) の見積もりは正しい。
- n = 10⁴ だと約 5×10⁷ 回。Python では 1 秒あたり 10⁷ 回程度が目安なので、通るとしてもかなり遅い。Follow-up が「O(n²) 未満」を求めているのはこのため。
- 内側のループを `j in range(i + 1, n)` から始めれば、同じ要素の 2 回使用と重複ペアを同時に避けられる。

**方針 2（ソート + 二ポインタ）**

- 「`nums[0] + nums[x] > target` なら `nums[x]` は最小の相手と組んでも大きすぎるので除外できる」という論証はとても良い。これが二ポインタの正しさの核心。
- 同じ理屈を左側にも適用してみよう: `nums[l] + nums[r] < target` のとき、`nums[l]` は **残っている最大の相手** と組んでも足りない。すると `nums[l]` について何が言える？ — これが書けると、方針 2 の if/elif/else が「大きい → r を左へ／小さい → l を右へ」の 2 行に整理できる。
- 計算量: ソート O(n log n) + 探索 O(n) = **O(n log n)**。見積もりは正しい。
- ⚠️ **見落とし**: この問題が返すのは **値ではなく元のインデックス**。`nums.sort()` すると位置が入れ替わってしまう。ソート前の位置をどう保持するか考えてみよう（ヒント: [配列のソート — 元のインデックスを保ったままソートする](../../notes/python/sort.md#元のインデックスを保ったままソートする)）。その分、空間は O(n) になる。
- ループ条件を `l < r` にすれば、同じ要素を 2 回使うことはない。`[3, 3]` も正しく扱えるか、手でトレースしてみるとよい。
- 仕組みの図解: [二ポインタ（尺取り法）](../../notes/patterns/two-pointers.md)

**別解のヒント**

- 問題文の Hint 3「配列を変えずに、追加の空間を使って探索を速くできないか？」を考えてみよう。
  方針 1 の内側ループがやっているのは「`target - nums[i]` が配列のどこかにあるか探す」こと。この「探す」を O(1) にできるデータ構造は？
  → 詰まったら [「見たものを覚えておく」ハッシュマップ](../../notes/patterns/hashmap-lookup.md)
- それができると時間 O(n)・空間 O(n) で、方針 2 よりも速くソートも不要になる。

| 方針 | 時間 | 追加空間 | 一言 |
| --- | --- | --- | --- |
| 1. 全探索 | O(n²) | O(1) | まず正しい答えを出す基準 |
| 2. ソート + 二ポインタ | O(n log n) | O(n)（インデックス保持） | 3Sum などに発展しやすい |
| 3. ハッシュマップ | O(n) | O(n) | この問題の想定解 |

### 2026-10-24（方針2改善への講評）

**`(値, インデックス)` の組でソート** — 正しい。答えのペアが見つかった瞬間に元のインデックスがそのまま取り出せる。空間は O(n)、時間はソートが支配的で O(n log n)。方針 2 の完成形としてこれで十分。

**インデックスを持たずに後から探す案** — 計算量の議論は正しい（後から探すのは O(n)、全体はソートの O(n log n) が支配的）。ただし 2 点注意:

- ⚠️ **同じ値が 2 つあるケース**を試してみよう。`nums = [3, 3]`, `target = 6` で、見つかった値 `3` と `3` の元インデックスを「配列を頭から探す」（例えば `nums.index(3)` を 2 回）で求めると何が返る？ 2 つ目の値は「1 つ目とは別の位置」から探す必要がある。
- 元の配列を後で探すには、ソート前の `nums` を残しておく必要がある。`sorted(nums)` で別リストを作るなら結局 O(n) の追加空間を使うので、空間の点では組でソートする案と同じ。コードも組でソートする案の方が単純。

**ループの終了条件** — 結論として `l == r` になる周回まで回しても、**この問題では**正しく動く。ただし「`l == r` の周回までに必ず答えが出る」は少し不正確:

- 実際には **`l == r` になる前に必ず答えが見つかる**。答えのペアを `(i, j)` とすると、`l <= i` かつ `j <= r` の間はどちらのポインタも答えを飛び越えない（飛び越えるには、答えの片方を「誰とも組めない」と判定して捨てる必要があるが、それは起こらない）。だから `l` と `r` は答えの位置より内側に入れず、`l < r` のうちに `(i, j)` に到達する。
- 一方で `l == r` の周回を許すと `nums[l] + nums[l]`、つまり **同じ要素を 2 回使った和** を判定してしまう。「解が必ず存在する」という保証がない場合を考えると、`nums = [1, 3, 4]`, `target = 6` が反例:
  - `1 + 4 = 5 < 6` → l を右へ
  - `3 + 4 = 7 > 6` → r を左へ
  - `l == r == 1`: `3 + 3 = 6` → 誤ってインデックス (1, 1) を返す
- 「同じ要素は使えない」をそのままコードにするなら `while l < r:`（＝ `l == r` になったら終わり）。こう書いておけば、解の保証に頼らずに正しいと言える。Two Sum II や 3Sum に発展させたときも同じ書き方で済む。
- 「`l == r` のように誤っておかず、`l > r` のように」の部分は、「ループを続ける条件」と「ループを止める条件」のどちらのつもりで書いたかが読み取りにくい。メモでは **`while` に書く式（続ける条件）** で書くと誤解がない。
